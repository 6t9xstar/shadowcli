## 1. What exactly are they asking you to build?

They want you to create the initial working version of ShadowCLI with three core capabilities:

| Phase                   | What they want                | Expected result                                 |
| ----------------------- | ----------------------------- | ----------------------------------------------- |
| 1. Filesystem isolation | OverlayFS temporary layer     | Agent changes don't modify original files       |
| 2. Security isolation   | Landlock + Linux namespaces   | Agent cannot freely access the host             |
| 3. Review engine        | Diff + approval interface     | Developer reviews changes before applying       |
| 4. CLI integration      | Rust command-line application | Developer can launch commands through ShadowCLI |

### The first milestone

The initial version should support a workflow like this:

```
shadow run -- ./agent-task.sh
```

ShadowCLI should:

1. Create a temporary sandbox.
2. Mount the project into an isolated filesystem.
3. Execute the requested command inside the sandbox.
4. Capture all file modifications.
5. Show a readable diff.
6. Ask the developer to approve or reject changes.
7. Apply approved changes to the original project.
8. Clean up the temporary sandbox.

The most important requirement: If the agent deletes `.env`, modifies Git files, or installs packages inside the sandbox, the original project must remain unchanged until approval.

## 2. Important technical corrections

Before implementing, make sure your AI coding assistant understands these points:

- OverlayFS: Mounting usually requires privileges or a properly configured user namespace. Detect unsupported environments and fail safely.
- Landlock: Restrict filesystem access using explicit allowlists. Do not assume it automatically protects every sensitive file.
- Namespaces: Isolate mount, PID, and network namespaces where supported.
- seccomp: Use a carefully tested syscall allowlist or deny policy. Blocking a few dangerous syscalls alone does not make a sandbox secure.
- Review engine: Never blindly copy the entire OverlayFS upper directory into the original project. Handle deletions, symlinks, path traversal, and conflicting changes safely.
- Security testing: A successful normal execution is not enough. You need tests that actively attempt to escape the sandbox.

ShadowCLI intercepts commands executed by AI coding agents, runs them inside an isolated environment, captures all filesystem changes, and allows developers to review and selectively approve those changes before they reach the original project.

The goal is to provide developers with a secure and lightweight alternative to giving autonomous AI agents unrestricted access to their host operating system.

## 4. Phase 1 — Filesystem Isolation

Implement a filesystem isolation engine.

Requirements:

- Accept an existing project directory.
- Create a unique temporary sandbox session.
- Preserve the original project as the read-only base.
- Create an isolated writable filesystem layer.
- Capture new files, modifications, and deletions.
- Prevent sandboxed commands from modifying the original project.
- Store session metadata and filesystem changes.
- Support cleanup of temporary sessions.
- Detect whether OverlayFS is supported and available.
- Handle mount failures safely.

The implementation must never silently fall back to executing commands directly against the host filesystem.

If OverlayFS is unavailable, report the limitation and provide a safe alternative or fail closed.

## 5. Phase 2 — Linux Security Isolation

Implement defense-in-depth security.

### Namespace isolation

Use Linux namespaces where supported:

- Mount namespace
- User namespace
- PID namespace
- Network namespace
- IPC namespace

Use unprivileged execution wherever possible.

Do not require unrestricted root privileges.

### Landlock

Implement filesystem access restrictions.

The sandbox should:

- Access only explicitly permitted project and runtime directories.
- Prevent access to SSH keys, credentials, unrelated projects, and sensitive host directories.
- Restrict filesystem writes to the isolated writable layer.
- Handle symlinks and path traversal safely.
- Apply restrictions before executing untrusted commands.

### seccomp

Implement a carefully designed syscall restriction policy.

Requirements:

- Default-deny or carefully restricted syscall policy where practical.
- Explicitly document permitted syscalls.
- Prevent dangerous privilege escalation paths.
- Handle architecture-specific syscall differences.
- Include a configurable security policy.

Do not claim that seccomp alone provides complete sandbox security.

## 6. Phase 3 — Command Execution Engine

Implement a secure process execution engine.

Requirements:

- Execute commands without shell interpolation by default.
- Support explicit shell execution when requested.
- Capture stdout and stderr.
- Track process exit codes.
- Handle process termination and timeouts.
- Prevent unauthorized child processes from escaping isolation.
- Support environment variable filtering.
- Prevent automatic exposure of host credentials.
- Support configurable network access.
- Record execution metadata.

The engine must not execute commands directly on the host when sandbox initialization fails.

## 7. Phase 4 — Shadow Diff Engine

After execution, generate a detailed report of all filesystem changes.

The report should include:

- Added files
- Modified files
- Deleted files
- File permissions changes
- Symlink changes
- Binary file changes
- Total changed files
- Execution status

Provide readable terminal output and Git-compatible unified diffs.

Do not expose sensitive file contents in logs or terminal output unnecessarily.

## 8. Phase 5 — Developer Review Gate

Implement an interactive review interface.

Requirements:

- Review individual file changes.
- Approve selected changes.
- Reject selected changes.
- Approve all changes.
- Discard the entire session.
- Display the exact destination of each approved change.
- Detect conflicts if the original project changes after sandbox execution.
- Prevent overwriting unrelated host files.
- Safely handle file permissions and symlinks.

The developer must explicitly approve changes before they are applied to the original project.

Use a safe, transactional application process where practical.

If applying changes fails, report the exact failure and preserve enough session data for recovery.

Create automated tests covering:

- Create a new file.
- Delete a file.
- Attempt to modify files outside the project.
- Attempt to read SSH credentials.

### Process isolation

- Attempt to access host processes.
- Attempt unauthorized network access.
- Attempt privilege escalation.

### Review engine

- Approve a modification.
- Reject a modification.
- Approve selected files.
- Detect conflicts.
- Handle interrupted execution.
- Recover from failed change application.

Tests must verify that rejected changes never modify the original project.

Do not run destructive security tests against the actual host operating system. Use disposable test environments.

## 4. My advice for your first development session

Don't ask your AI to build the entire project in one shot.

Start with the repository audit, then build a working filesystem-isolation demo that proves this:

```
Original project:
    main.rs → ORIGINAL

AI agent executes:
    echo "MODIFIED" > main.rs

ShadowCLI:
    main.rs → ORIGINAL
    Sandbox:
        main.rs → MODIFIED

Developer rejects:
    main.rs → ORIGINAL

Developer approves:
    main.rs → MODIFIED
```

Once this works reliably, add Landlock, namespaces, seccomp, and the review engine in stages.

This first proof of concept is the foundation of ShadowCLI. If you get the isolation and approval model right, the rest of the product becomes much easier to build safely.
